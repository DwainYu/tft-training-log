> **本文只做设计与技术演进路线。本次不实现任何 OCR。**

---

## 1. 定位与唯一原则

```
正确做法（本项目的目标）

截图 → 预处理 → OCR/图像识别 → 结构化候选 → 用户确认/修改 → 生成对局记录
                                                  ↑
                                            绝不能省略这一步

错误做法（明确不做）

截图 → OCR → 直接保存
```

理由很简单：训练数据的价值在于**归因正确**。OCR 错一个名次，统计就错一整条趋势线，
而用户并不知情。与其事后在统计里发现异常，不如在录入时用一次点击确认。
这也和 README 里「统计数据不替你下结论」的定位一致。

因此本功能的第一句设计约束是：

> **OCR 只是识别系统的一部分；人工确认是流水线的一环，不是可选项。**

## 2. 六段流水线

### ① 截图 Screenshot

- 输入方式：粘贴（`paste` 事件）/ 拖拽 / 文件选择。
- 支持多张：一局通常会有「结算面板」和「阵容/棋盘」两张（见 §3）。
- 不主动请求任何权限，不读剪贴板之外的内容。

### ② 预处理 Preprocessing

目的只有一个：**提高下一环的输入质量**，不做「聪明的还原」。

| 步骤 | 说明 | 必要性 |
| --- | --- | --- |
| 尺寸归一化 | 超长图压缩到模型/引擎友好的短边 | 高 |
| 图像类型判别 | 结算面板 / 棋盘 / 商店 / 未知 —— 决定走哪套解析器 | 高 |
| 区域裁剪（可选） | 结算面板里数字块的行列位置是稳定的，可只喂关键区域 | 中（V2 再考虑） |
| 对比度 / 去噪 | 亮度统一，减少误识 | 中 |
| 转灰度 | 文字 OCR 前常用 | 中 |

### ③ 识别 OCR / Vision

两条能力轨道，**必须分开设计**（这是用户特别强调的点）：

| 轨道 | 负责 | 技术形态 |
| --- | --- | --- |
| **文字 OCR** | 名次、玩家名、阶段、等级、金币、阵容名、海克斯名 | 文本识别（tesseract.js / PaddleOCR-wasm / 云端 API） |
| **图标 / 图像匹配** | 棋子、装备、海克斯图标、羁绊图标 | 模板匹配 / 局部特征 / embedding 相似度 |

**关键判断：图标识别未来大概率会成为独立能力，甚至独立于 project 存在。**
因此接口上不能把「一次识别」当成一个整体 —— 必须是「多个探测器 + 多个解析器」的可插拔结构：

```ts
// 未来形态（现在不要实现，仅确定接口方向）
interface Recognizer<T> {
  key: string;                                  // "text.placement" / "icon.augment"
  supports(imageType: ImageType): boolean;
  recognize(input: ProcessedImage): RecognizedField<T>[];
}

interface RecognizedField<T> {
  field: keyof MatchDraft;
  value: T;
  /** 0–1。低于阈值的一律不自动选中，只作为候选呈现 */
  confidence: number;
  /** 截图中的证据位置，用于 UI 上高亮「我是从这儿读出来的」 */
  evidence?: { x: number; y: number; w: number; h: number };
  source: string;                               // 哪个 recognizer 得出的
}
```

`evidence` 是产品层面的关键：让用户能**看见**识别是从哪个区域读出来的，
纠错的信任成本会低一个量级。

### ④ 结构化候选 Structured Draft

把识别出的字段拼成一个 draft —— 而且要经过**与人工录入完全相同的校验**：

```
候选字段
  ↓ 归一化（这里直接复用 Phase 3A 的成果）
  ↓   · composition → normalizeCompositionKey()
  ↓   · augment / item / unit → 静态数据 id（模糊匹配 + 人工兜底）
  ↓ ManualAdapter.toMatchInput()   ← 和手打走同一条路
  ↓ validateMatchInput() + validateMatchStaticData()
  ↓
ImportDraft { fields: Field<>, imageRef?, createdAt, status: 'draft' }
```

**这里是本方案里最重要的复用点**：
`src/data/adapters/types.ts` 的 `DataSourceAdapter` 已经定义了「任何来源都产出 `MatchInput`」。
截图 adapter 要走这条路，而不是写一条新的落库逻辑。

### ⑤ 用户确认 User Confirmation

UI 形态（尚未实现，此处定形态）：

```
┌───────────────┬────────────────────────────────┐
│  原始截图      │  候选字段                       │
│  （可框选对比） │  名次   8      [低置信度 ⚠] [改] │
│               │  阶段   4-5    [ok]             │
│               │  等级   7      [ok]             │
│               │  阵容   福牛    [未确认] [改]     │
│               │  海克斯 A/B/C  [部分匹配]        │
│               │  ─────────────────────────      │
│               │  [放弃]        [确认并保存]      │
└───────────────┴────────────────────────────────┘
```

规则：

- **低置信度字段不高亮自动选中**，必须显式确认。
- 每个字段都可以改，改的过程应该走和手打**同一个 Selector**（阵容三层选择、海克斯搜索）。
- 允许「只保存我确认过的部分」—— 其余留空，不要拿候选值冒充事实。
- 允许一次性「标记为不可识别」，避免下次同一张图再浪费时间。

### ⑥ 落库 Match Record

- 走 `addMatch()` → 写完进入普通对局流程（可继续详细信息 / 复盘）。
- 保存后可以：

```
候选 →  若用户在确认界面修改了某个 OCR 结果，
                          该「原值 → 改后值」记录到纠正日志
                                    ↓
                          下次同区域 / 同模式的候选排序参考
```

这是**唯一建议做的「学习」**：不用训练模型，只用一张纠正表做同模式优先级重排。
把它放在最后，且规模有限。

## 3. 能识别哪些字段

> 置信度是**预期**，不是承诺。每张截图来源不同（分辨率、UI 版本、是否开了滤镜），
> 实际效果要在真机上验证。下表用于规划 UI 的「默认是否免确认」。

### 3.1 依赖文字 OCR 的字段

| 字段 | 来源区域 | 预期置信度 | 默认免确认 | 备注 |
| --- | --- | --- | --- | --- |
| 名次 `placement` | 结算面板 | **高** | ✅ | 数字大概率干净 |
| 玩家名 / 自己的条目定位 | 计分板行 | 中 | ⬜ | 需要定位「我是哪一行」 |
| 阶段 `stage/round` | 结算面板顶部 | 中 | ⬜ | 形如 `4-5`，正则可校验 |
| 等级 `finalLevel` | 结算面板 | 中高 | ✅ | 有小图标辅助，易混淆 UI 元素 |
| 金币 `totalGold` | 结算面板 | 中 | ⬜ | 位置不稳定 |
| 血量 `finalHealth` | 结算面板 | 中 | ⬜ | 与 UI 血条可能冲突 |
| 海克斯名 `augments[]` | 计分板 / 结算面板 | 中 | ⬜ | 名字长、可能有换行 → 需匹配 `augmentRepository` |
| 阵容名 `composition` | 手动为主 | — | ⬜ | 多数 UI 不显示阵容名，见下 |

### 3.2 依赖图标 / 图像匹配的字段

| 字段 | 来源 | 预期置信度 | 备注 |
| --- | --- | --- | --- |
| 棋子 `coreUnits[]` | 棋盘 / 计分板头像 | 中 | 需要去重 + 星级区分 |
| 装备 `coreItems[]` | 棋子身上的装备条 | 中低 | 重叠、裁剪、旋转都会影响 |
| 羁绊 `traits[]` | 羁绊栏 | 中 | 图标 + 数字 tier 都要读 |
| 海克斯图标 | 海克斯栏 | 中 | 名称 OCR 的交叉验证来源（**两条轨道互相印证**是好设计） |

### 3.3 大概率识别不到、必须人工的字段

- 阵容名 `composition` —— 大多数结算 UI 不显示阵容名。
  因此截图录入**不能指望解决阵容字段**，它要靠 Phase 3A 的选择器。
  这正是「先做 Phase 3A，再做 OCR」顺序的技术依据。
- 所有复盘字段（开局意图、失败原因、下一局练什么）—— OCR 永远读不到。
- 训练 Session 归属 —— 可以猜（按时间），但应默认继承当前 Session。

### 3.4 通过 Dropdown 无法回答，但可以从图上算出来的

- `durationSeconds`：如果有阶段记录可反推近似值；**建议留空**，不要编造。

## 4. 错误处理

| 场景 | 处理 |
| --- | --- |
| 识别引擎加载失败 / 不支持 | 流水线降级到「手动」：仍然显示截图，全部字段手动填。**不允许静默失败** |
| 图片不是 TFT 结算画面 | ② 阶段就判为 unknown 并提示用户，不浪费时间跑 OCR |
| 某个字段低于阈值 | 不高亮、不自动选中，显示为「未确认（灰色）」 |
| 多个候选冲突（如两个可能的名次） | 并列列出，让用户点。不要取最高分蒙一个 |
| 部分字段成功 | 允许只保存已确认部分，其余留空 |
| 用户改了 OCR 结果 | 记录到纠正日志（见 §2-⑥），但不做任何自动推广到全局规则的动作 |
| 保存失败 | 保留 draft，不要丢用户的编辑 |

原则：**宁可少填，不可错填。** 一个空字段的成本远低于一个错误字段。

## 5. 置信度怎么用

- 阈值不写死在代码里，**按字段配置**（名次可以高阈值自动选中，装备一律手确认）。
- 分三档展示：

| 档位 | UI | 行为 |
| --- | --- | --- |
| 高（≥0.85） | 正常选中态 | 一眼能扫过去 |
| 中（0.5–0.85） | 带浅色 ⚠ | 需要点一下确认 |
| 低（<0.5） | 灰色未确认 | 必须手选或手填 |

- 置信度要能被**交叉验证提升**：例如海克斯名字 OCR 得 0.7，但图标匹配到同一个 id 且 0.9
  → 合并后提升到「高」。这是把两条轨道分开设计带来的直接收益。

## 6. 是否保存原始截图

**建议：默认不保存，可显式开启。**

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 保存原图到 IndexedDB | 可回溯核对、未来可重跑更好的识别器 | 体积大（几百 KB–几 MB/张）；JSON 导出会爆炸；含个人信息（其他玩家昵称） |
| 只存缩略图 | 体积小 | 无法重跑识别 |
| **默认不存，用户显式开启后存**（推荐） | 默认隐私友好 | 需要一次小白说明 |

若开启保存，规则：

- 存**压缩后的 JPEG/WebP 缩略图**（≤1600px 短边），不存原图。
- 单独一张 `screenshotAssets` 表，用 `assetId` 引用，**不塞进 `Match`**。
- 导出 JSON 时默认**不含图片**（提供开关）。
- Data 页存储概况里显示图片占用，并提供一键删除全部截图。
- 删除对局时级联删除其截图。

## 7. 隐私与本地数据

红线（与 README 的 Privacy 章节一致，OCR 不能例外）：

- 图片**只在本机处理**。任何云端 OCR 方案都必须：默认关闭 + 明确提示 + 用户逐次授权。
- 项目自身不发请求；使用第三方服务的行为要能被看见。
- 截图包含**其他玩家昵称** —— 即使只本地保存也应在 UI 上说明一句。
- 不要自动批量扫描用户的截图文件夹。始终由用户主动选择图片。
- 导出包包含图片时要有清晰提示（因为这会把别人的昵称也带进备份文件）。

## 8. 技术演进路线 V1 / V2 / V3

### V1 — 基础文字与数字

**目标**：证明「截图 → 候选 → 确认 → 落库」这条流水线跑得通。

- 范围：仅结算面板的**文字与数字**
- 字段：名次、阶段、等级、金币（先做最有把握的 3–4 个）
- 识别：纯文字 OCR，**不做**任何图标识别
- UI：候选面板 + 逐字段确认 + 跳过
- 图片：**不落盘**（处理完即丢）
- 前置依赖：
  - `DataSourceAdapter`（✅ 已有）
  - 一个 `ScreenshotAdapter`（待写，产出 `MatchInput`）
  - 一个 `ImportDraft` 的临时容器（可用 React state，暂不入库）
- 验收标准：能在 ≤ 3 次点击内把一张结算图变成一条对局记录，且**每个数字都经过用户确认**
- 优先级：**P3**（前面所有地基完成后才有意义）

> 建议把 V1 当成一次 spike：先手动准备好 20 张真实截图，跑出一个真实准确率，
> 再决定要不要投入。不要先把 UI 做漂亮再看效果。

### V2 — 海克斯 / 装备 / 阵容名

- 增加第二条轨道：**图标匹配**（海克斯 / 装备 / 羁绊）
- 海克斯名 OCR × 图标匹配交叉验证，提升置信度
- 「我的常用」「最近使用」参与候选排序 —— **这里直接用 Phase 3A 的成果**
- 装备持有者推断（哪个棋子带的哪件）：先做「不确定就留空」
- 涉及的 UI：海克斯 Selector 要支持「三个槽位」模式（与复盘模板共用组件）
- 优先级：P3

### V3 — 完整棋盘 / 棋子 / 装备 / 羁绊 / 阶段

- 棋盘级识别：棋子在格子上 → 站位信息
- 羁绊 tier 数字识别
- 多图：同一局的「2-x / 3-x / 4-x / 结算」多张一起导入 → 自动长出 Timeline
  （与 Phase 4 的 Timeline 是同一套组件）
- 原图（缩略图）可选保存 + 在 Timeline 上标注
- 优先级：P3，且**很可能是过度工程** —— 到这一步应该重新评估，
  到这一步应该停下来重新评估：「用它替代手写」是否真的划算。

## 9. 数据模型影响（登记，不在本次做）

| Current | Problem | Suggested evolution | Migration impact |
| --- | --- | --- | --- |
| 只有 `matches / decisions / reviews / trainingGoals / trainingSessions / settings` 六张表 | 草稿、原图、纠正日志都无处安放 | Dexie v3 起新增：`importDrafts`（可选入库）、`screenshotAssets`（可选）、`recognitionCorrections`（可选） | 全部是**新表**，旧记录不受影响 |
| `Match` 没有来源标记 | 无法区分「这是手打的还是 OCR 来的」，也就无法只对 OCR 记录做质量回溯 | `Match.source?: DataSourceKey`（适配 `DataSourceKey` 已存在）+ `Match.importMeta?`（confidence 摘要、draftId） | **加法式**，旧记录无此字段即视为 manual |
| `DataSourceAdapter` 只实现了 ManualAdapter | 目前没有第二条落地路径 | 新增 `ScreenshotAdapter: DataSourceAdapter<ScreenshotPayload>`，`key: 'screenshot'` 已在 union 里 | 无需迁移 |
| 图片无处放 | — | `screenshotAssets` 表 + `Match.screenshotAssetIds?: string[]` | 导出需考虑是否包含二进制/base64 |

**注意**：不要在 V1 就把上面全部建出来。V1 只需要 `ScreenshotAdapter` +
（可选的）`Match.source`；其余等真正需要保存草稿/图片时再说。
